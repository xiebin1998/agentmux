# AgentMux 开发与打包指南

本文所有命令都在本机实测过。凡未实测成功的步骤都明确标注了「未验证」，不含猜测。

---

## 一、环境要求

| 依赖 | 实测版本 | 说明 |
|---|---|---|
| Node.js | v24.18.0 | 前端构建 |
| Rust（MSVC 工具链） | stable | 后端编译 |
| cargo-tauri CLI | 2.11.4 | 缺则 `cargo install tauri-cli --version "^2"` |
| WebView2 Runtime | — | Win11 自带；Win10 可能需要单独安装 |
| WiX 3.14 / NSIS 3.11 | — | **仅打包安装包时需要**，首次打包自动下载，公司网络可能失败，见 §3.3 |

## 二、开发调试

### 2.1 首次准备

```bash
cd D:\workSpase\idea\agentmux\frontend
npm install
```

### 2.2 一键启动（推荐）

```bash
cd D:\workSpase\idea\agentmux
cargo tauri dev
```

它会依次：执行 `cd ../frontend && npm run dev`（Vite 开发服务器，http://localhost:5173）→ 编译 Rust（debug）→ 打开窗口并加载 devUrl。改前端热更新，改 Rust 自动重启。

> ⚠️ **踩过的坑**：`beforeDevCommand` / `beforeBuildCommand` 的**工作目录是 `src-tauri`**，所以配置里必须写 `cd ../frontend ...`。原来写的 `cd frontend` 会报 `系统找不到指定的路径` 而直接构建失败（已修正）。

### 2.3 分体调试（只改前端时不必让 Rust 重启）

```bash
# 终端 1：只跑前端
cd frontend && npm run dev

# 终端 2：启动窗口，但不让它自己再拉一个 Vite
cd src-tauri && cargo tauri dev --no-dev-server
```

其它有用的开关：`--no-watch`（不监视 Rust 改动）、`--port <端口>`、`--exit-on-panic`。

### 2.4 只做检查，不启动窗口

```bash
cd src-tauri && cargo check      # 类型检查
cd src-tauri && cargo test       # 24 个单测（另 3 条需真实环境的 opt-in 测试默认跳过）
cd frontend  && npm run build    # tsc 类型检查 + vite 构建，同时产出 frontend/dist
```

> ⚠️ 跑 `cargo build` / `cargo test` **之前先确认没有 `agentmux.exe` 在运行**，否则链接会报
> `LNK1104: 无法打开文件 ...\target\debug\agentmux.exe`。先关掉再构建。

### 2.5 不经过 tauri CLI，直接跑（验证后端最快）

```bash
cd frontend && npm run build          # 先产出 dist，否则窗口是白的
cd src-tauri && cargo build
.\target\debug\agentmux.exe
```

## 三、打包

### 3.1 生成安装包

```bash
cd D:\workSpase\idea\agentmux
cargo tauri build
```

> ⚠️ **必须在仓库根目录执行**（不要在 `src-tauri` 里跑）。`beforeBuildCommand` 里的
> `cd ../frontend` 是按仓库根目录解析的；在 `src-tauri` 下执行会报
> `系统找不到指定的路径`。（本机实测踩过两次）

> ⚠️ **打包前先关掉正在运行的 AgentMux**，否则最后一步复制产物会失败：
> `failed to remove file ...agentmux.exe: 拒绝访问 (os error 5)`。

产物（`bundle.targets` 当前为 `all`，**三项均已实测生成**）：

- `target\release\agentmux.exe` —— 免安装可执行文件，12.2 MB
- `target\release\bundle\msi\AgentMux_0.1.0_x64_en-US.msi` —— MSI 安装包，4.3 MB
- `target\release\bundle\nsis\AgentMux_0.1.0_x64-setup.exe` —— NSIS 安装程序，3.0 MB

> 首次打安装包需要从 GitHub 下载 WiX 与 NSIS，本机直连会失败 —— **挂代理即可**，见 §3.3。

只打其中一种：

```bash
cargo tauri build --bundles msi
cargo tauri build --bundles nsis
```

### 3.2 只要可执行文件，不生成安装包（**已实测通过**）

```bash
cargo tauri build --no-bundle
```

产出 `target\release\agentmux.exe`，可直接拷给别人双击运行。

### 3.3 网络受限时的打包（**本机当前就是这个情况**）

实测报错：

```
Downloading https://github.com/wixtoolset/wix3/releases/download/wix3141rtm/wix314-binaries.zip
Error failed to bundle project: `timeout: global`
```

`curl` 复测确认 GitHub release 资源下载连不上（21 秒后 `Failed to connect to github.com port 443`）。三种办法：

**A. 走代理（最省事，已实测可用）**

本机代理在 `127.0.0.1:7897`（Clash 系默认混合端口），挂上代理后 WiX 与 NSIS 都自动下载成功、两个安装包都打出来了：

```bash
# Git Bash
HTTP_PROXY=http://127.0.0.1:7897 HTTPS_PROXY=http://127.0.0.1:7897 cargo tauri build

# cmd / PowerShell
set HTTP_PROXY=http://127.0.0.1:7897
set HTTPS_PROXY=http://127.0.0.1:7897
cargo tauri build
```

（端口换成你自己的代理；Tauri 的下载器会读这两个环境变量）

> 先确认代理能用：`curl -x http://127.0.0.1:7897 -o /dev/null -w "%{http_code}" https://github.com`，返回 200 即可。

**B. 手动把工具放进缓存目录（不用代理）**

Tauri 的工具缓存根目录取 `dirs::cache_dir()`，Windows 上即 `%LOCALAPPDATA%\tauri`：

```
%LOCALAPPDATA%\tauri\WixTools314\    ← WiX 解压后的内容
%LOCALAPPDATA%\tauri\NSIS\           ← NSIS 解压后的内容
```

所需文件：

- WiX：下载 `wix314-binaries.zip` 解压，目录内需含
  `candle.exe`、`candle.exe.config`、`darice.cub`、`light.exe`、`light.exe.config`、
  `wconsole.dll`、`winterop.dll`、`wix.dll`、`WixUIExtension.dll`、`WixUtilExtension.dll`
- NSIS：`nsis-3.11.zip` 解压，另需官方 `nsis_tauri_utils.dll`

**关键区别**：**WiX 只校验文件是否存在** → 手动放进去就能生效；
**NSIS 还会校验文件哈希** → 版本不一致会被判定"mis-hashed"并重新下载。
所以受限网络下建议**先只打 MSI**：

```bash
cargo tauri build --bundles msi
```

**C. 干脆不打安装包**：用 §3.2 的 `--no-bundle`，直接交付裸 exe。

### 3.4 打包时自动做了什么

1. 运行 `build.beforeBuildCommand`（即 `cd ../frontend && npm run build`）
2. 用 `build.frontendDist`（`../frontend/dist`）把前端资源打进二进制
3. 按 `bundle.targets` 生成安装包，并按 `bundle.icon` 设置图标

## 四、配置与数据位置（都不在仓库里）

所有内容都放在**同一个可迁移的数据目录**下（默认为 `%APPDATA%\agentmux`）：

| 内容 | 路径 |
|---|---|
| 数据目录指针 | `%APPDATA%\agentmux\location.json`（固定留在系统盘） |
| 配置文件 | `<数据目录>\settings.json` |
| 数据库 | `<数据目录>\agentmux.db` |
| ndjson 归档 | `<数据目录>\archive\<日期>.ndjson` |

**迁移**：设置页「数据位置」→「迁移到这里」会选一个目录，把配置 + 数据库 + 归档整体搬过去；
「恢复默认位置」搬回 `%APPDATA%\agentmux`。指针文件 `location.json` 不跟着搬，它负责记住
当前数据目录在哪，所以装在 D 盘、数据放 E 盘都能找到。

⚠️ **自动回复默认是关闭的**（只记录、不发送）。要开启请到「设置」页勾选。

⚠️ **身份按 IM 平台分别配置**（不存在跨平台的「全局身份」）：在「运行总览」或项目的
IM 卡片里设置该平台下你自己的账号标识，用于跳过自己发的消息。

⚠️ **自动压缩按上下文百分比触发**：滑块 0~100，程序按项目的上下文上限换算成字符数。

## 五、界面里怎么用

模型：**项目 → 会话**。监听、回复设置、工作目录都是**按项目**的。

1. **提供方检测**页：确认「钉钉 CLI」与「Agent CLI」都被检测到（列表里**单选**即可，不需要手输路径；
   检测等价于在终端敲 `dws version` / `qodercli --version`）
2. **创建项目**：填项目名；工作目录可手输，也可点「选择…」用系统目录窗口挑；
   IM 平台与 Agent 平台各选一项
3. **启动监听**：**在左侧项目行内**点该项目自己的「@我」或「单聊」。
   两个开关互相独立、可并发；状态显示为**监听中**才算真正生效（以 ready 信号为准）
4. **启用回复**：在项目的「编辑」里勾「启用自动回复」并设超时/字数/上下文；
   「设置」页只放**全局**项（Agent 启动参数、压缩百分比、数据位置）
5. **看运行情况**：「运行总览」「实时事件流」「回复历史」「监听日志」「提供方检测」五个视图
6. **会话**：收到消息后，会话自动出现在**对应项目**下面；点它看消息流与回复
7. **作废会话**：在会话的右侧面板「作废并重建会话」——只影响**该项目**的 Agent 会话记录

> ⚠️ 监听与回复设置是**按项目隔离**的，改完设置需要**重启该项目的监听**才生效
> （不再是全局单例的"保存即生效"）。
>
> ⚠️ 升级前已有的历史事件 `project_id` 为空，**不会挂在任何项目下**：它们集中显示在
> 左树的「未归类（历史会话）」分组里，选一个项目点「归入」即可出现在该项目下。

## 六、常见问题

| 现象 | 原因与处理 |
|---|---|
| `beforeBuildCommand` 失败：`系统找不到指定的路径` | before 命令的工作目录是 `src-tauri`，路径必须写 `../frontend`（已修） |
| `LNK1104: 无法打开文件 ...agentmux.exe` | 有实例正在运行锁住了产物，先结束它再构建 |
| 打包卡在 `Downloading ...wixtoolset...` | 网络问题，见 §3.3 |
| 监听窗口一直 `received 0 event(s)` | ① 看 `dws event status` 的 **Consumers 表有没有多余的僵尸消费者**在抢事件（曾因此收不到消息）；② 确认真的有人 **@ 了你本人**；③ 确认 `bus` 处于 `running` |
| 改了设置不生效 | 回复开关、超时、字数上限、上下文预算保存后**即时生效**；**Agent / IM CLI 路径变更需要重启对应监听**（该项即需求台账里的 D-76，实现期确认） |
| 应用启动后一片空白 | 前端 `frontend/dist` 不存在。打包/dev 模式会自动构建；直接跑 debug 产物时需先 `cd frontend && npm run build` |
